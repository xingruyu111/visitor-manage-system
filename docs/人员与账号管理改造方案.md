# 人员管理与账号管理改造方案

> 依据：采购文档附件1 用户管理模块、附件2 第3/4项。
> 目标：人员类型作为审批身份与主角色来源，角色决定登录/功能权限；人员与账号按 `person_no`（工号/学号）一对一关联；手机号不做强关联，账号侧可独立修改。
> 本文是改造设计，不含代码实现。

---

## 一、已确认的设计决策

| 决策 | 结论 |
|---|---|
| 人员类型的作用 | 审批身份依据；新增/导入时按类型生成**主角色**；不直接参与权限判断 |
| 角色的作用 | 登录权限、功能权限、菜单/接口访问 |
| 人员与账号 | 一人一账号；按 **`person_no`（工号/学号）** 关联 |
| 账号关联字段 | 账号表保留 `person_no`，账号管理列表显示“工号/学号” |
| 人员手机号 | 人员档案联系电话，允许过期；仅用于初始开通账号 |
| 账号手机号 | 登录/微信绑定手机号，**独立维护**，可在账号管理修改；不与人员手机号强同步 |
| 主角色 | 由人员类型生成，**不可删除、不可单独停用**；只能随人员类型变更或人员停用而变化 |
| 修改人员类型 | 主角色同步替换；附加角色保持不变 |
| 删除人员 | 人员软删 + 账号停用 + 角色停用，数据不删 |
| 重新添加人员 | 按 `person_no` 找回原人员和原账号，恢复启用及历史数据 |
| 账号停用 | 系统管理员停用后立即无法登录（含已签发 token） |
| 停用前待办 | **阻止停用**：存在未处理审批任务时不允许停用，需先转交 |
| 角色冲突 | 本期不做互斥矩阵，后续按需增加 |
| 角色切换 | 支持一人多角色，应用内切换；默认角色 `is_default` |

## 二、现状与差距

| 现状 | 问题 | 改造 |
|---|---|---|
| `vst_staff` 有 `job_no`、`student_no` 两个字段 | 学号/工号不统一 | 新增 `person_no` 统一写入；旧字段保留兼容 |
| 人员与账号仅靠手机号匹配 | 人员手机号过期后关联断裂 | 改为 `person_no` 关联；账号表增加 `person_no` |
| 账号手机号与人员手机号混用 | 人员换号影响登录 | 账号手机号独立字段、独立维护 |
| `vst_user_role` 无来源标记 | 分不清主角色和附加角色 | 增加 `source`（IDENTITY/MANUAL） |
| 账号页 `assignRole` 是“替换唯一角色” | 不能真正多角色 | 改为角色增删接口 |
| 人员类型变更不更新角色 | 身份与权限不一致 | 事务内替换 IDENTITY 角色 |
| 人员停用只停角色，不改 `user.status` | 账号状态不彻底 | 人员停用同时 `user.status=0` |
| 账号停用会级联停用全部角色 | 重新启用后角色恢复困难 | 账号停用只改 `user.status`，角色保持；人员停用才级联 |
| 停用前不检查待办 | 审批任务卡死 | 待办存在则拒绝停用 |
| 新增人员不建账号 | 一人一号需要手工补 | 人员新增/导入自动开通账号并赋主角色 |
| 角色切换只有后端请求头 | 前端无入口 | 增加角色列表接口与切换器 |

## 三、数据模型改造

### 3.1 人员表

```sql
ALTER TABLE vst_staff ADD COLUMN person_no VARCHAR(64) NULL COMMENT '统一工号/学号' AFTER phone;
CREATE UNIQUE INDEX uk_staff_person_no ON vst_staff (school_id, person_no);
```

规则：

- `person_no` 为人员唯一业务编号，**新增/导入必填**；
- 教职工、学生、附属学校人员由数据中台提供学号/工号；
- 商户、食堂、校友由学校分配编号，同样写入 `person_no`；
- `job_no`、`student_no` 保留用于展示和旧数据兼容；
- 手机号必填，但只作为人员联系方式和账号初始手机号。

### 3.2 账号表

不建人员-账号映射表，直接在账号表冗余 `person_no`：

```sql
ALTER TABLE vst_user ADD COLUMN person_no VARCHAR(64) NULL COMMENT '关联人员工号/学号' AFTER phone;
CREATE UNIQUE INDEX uk_user_person_no ON vst_user (person_no);
```

规则：

- `person_no` 可空：系统管理员、保卫处管理员、门卫等无人员档案的账号为空；
- 一个 `person_no` 只能对应一个账号；
- 人员与账号通过 `staff.person_no = user.person_no` 关联；
- 人员手机号与账号手机号**互不强同步**：
  - 新建账号时，账号手机号默认取人员手机号；
  - 之后人员手机号变更不影响账号手机号；
  - 账号手机号可在账号管理单独修改，用于登录/微信绑定。

### 3.3 角色来源标记

```sql
ALTER TABLE vst_user_role
  ADD COLUMN source VARCHAR(16) NOT NULL DEFAULT 'MANUAL' COMMENT 'IDENTITY主角色/MANUAL附加角色';
```

约定：

- 每人最多一条 `source=IDENTITY`；
- 人员类型变更时删旧主角色、插新主角色；
- `source=IDENTITY` 的记录禁止删除/单独停用；
- 附加角色可增删，不影响主角色。

### 3.4 类型-角色映射表

```sql
CREATE TABLE vst_person_type_role (
  person_type TINYINT NOT NULL,
  role        TINYINT NOT NULL,
  description VARCHAR(64) NULL,
  updated_at  DATETIME NULL,
  PRIMARY KEY (person_type)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='人员类型默认角色';

INSERT INTO vst_person_type_role VALUES
 (1,5,'教职工',NOW()),(2,6,'学生',NOW()),(3,7,'校内商户',NOW()),
 (4,8,'食堂人员',NOW()),(5,5,'附属教职工',NOW()),(6,6,'附属学生',NOW()),
 (7,9,'校友',NOW());
```

### 3.5 数据迁移（026）

1. `vst_staff.person_no = COALESCE(job_no, student_no)`，缺失的标记待补；
2. `vst_user.person_no` 按 `user.phone = staff.phone` 回填；
3. 一个手机号匹配到多条人员时，列冲突清单人工处理，不自动选择；
4. 对已关联账号：角色等于人员类型映射角色时置 `source=IDENTITY`、`is_default=1`；
5. 其余角色统一 `source=MANUAL`；
6. 初始化 `vst_person_type_role`；
7. 加唯一索引前先清理重复 `person_no`。

## 四、核心业务规则

### 4.1 新增/导入人员

流程：

```
校验 person_no 必填且唯一、手机号必填
  → 按 person_no 找已有人员
      → 找到停用人员：恢复人员，复用原账号（不新建）
      → 未找到：新增人员
  → 按 person_no 找账号
      → 有：直接关联，不覆盖账号手机号
      → 无：创建账号，账号手机号 = 人员手机号，默认密码 123456
  → 按类型写入/修正 IDENTITY 主角色
  → 返回人员 + 账号状态
```

约束：

- `person_no` 重复 → 拒绝；
- 手机号已属于其他账号 → 创建账号时拒绝，提示先处理手机号冲突；
- 已有账号的附加角色不因导入被清空，只保证主角色存在；
- 人员手机号变化时，不自动改账号手机号。

### 4.2 修改人员信息

| 变更项 | 处理 |
|---|---|
| 姓名、部门、班级 | 更新人员；账号姓名可同步（建议同步） |
| 人员手机号 | 只改人员档案，不动账号手机号 |
| 人员类型 | 事务内替换 IDENTITY 主角色 |
| 状态 | 按 4.3/4.4 处理 |

修改人员类型：

1. 记录旧类型、旧主角色；
2. 更新人员类型；
3. 删除旧 `IDENTITY` 角色；
4. 插入新 `IDENTITY` 角色（同一角色则复用）；
5. 新主角色设为默认；
6. 附加角色不动；
7. 写审计日志。

### 4.3 删除人员（软删）

前置检查：

- 统计 `vst_approval_task` 中 `assignee_id=该账号 且 status=PENDING`；
- 大于 0 → 拒绝，返回“还有 N 条待审批，请先转交”。

通过后：

1. `staff.status=0`；
2. `user.status=0`；
3. 该用户全部角色 `status=0`；
4. 保留 `person_no`、历史预约、审批记录。

### 4.4 重新添加人员

- 按 `person_no` 匹配停用人员；
- 恢复同一 `staff.id`、同一 `user.id`；
- `staff.status=1`、`user.status=1`、角色 `status=1`；
- 若主角色缺失或类型已变，按当前类型重建；
- 账号手机号保持停用前的值，不强制用人员手机号覆盖。

### 4.5 停用/启用账号（系统管理员）

- 停用前同样检查待办，有则阻止；
- 停用：`user.status=0`，**不级联角色**；
- 启用：`user.status=1`，角色沿用停用前状态；
- 已签发 token：`AuthInterceptor` 每次请求校验 `user.status`，停用后立即 403。

### 4.6 主角色保护

接口层：

- 删除角色：若 `source=IDENTITY` → 400“该角色由人员类型决定，请修改人员类型或停用人员”；
- 停用角色：同上；
- 修改角色：不允许把 IDENTITY 改成其他角色，只能走“修改人员类型”。

### 4.7 多角色与切换

- 登录返回 `currentRole` 和角色列表；
- 前端顶部角色切换器；
- 切换时请求头带 `X-Current-Role`，后端校验该角色属于当前用户；
- 切换写审计日志；
- 默认角色取 `is_default=1` 的主角色；没有则取第一个启用角色。

### 4.8 审批链

- 被访人审批链按 **`staff.person_type`** 判断，与当前激活角色无关；
- 审批人处理任务时仍要求账号启用、角色启用、任务分配给本人；
- 保留运行时校验：申请人不能审批自己的预约；
- 角色互斥矩阵本期不做。

### 4.9 微信登录与手机号

现状与约束：

- 微信网页授权（公众号 H5）只能获取 openid/unionid/昵称头像，**拿不到手机号**；
- 小程序 `getPhoneNumber` 可以获取手机号；
- 企业微信网页授权可返回成员手机号；
- 运营商号码认证也能一键取号，但需采购服务。

建议流程：

```
微信授权 → 拿 openid
  → openid 已绑定账号：直接登录
  → 未绑定：
      能拿到手机号（小程序/企业微信/运营商）→ 匹配账号手机号 → 绑定 openid → 登录
      拿不到手机号（公众号 H5）→ 输入手机号 + 短信验证码 → 匹配 → 绑定 → 登录
```

- 账号手机号是微信登录匹配依据；
- 账号手机号修改后，openid 绑定保留，仍可登录；
- 人员手机号不参与微信登录匹配。

## 六、批量分配角色

场景：中台同步几万人后，需要批量授予“部门经办人”等附加角色。

### 方式一：规则批量（主）

1. 选择条件：人员类型、部门、班级、关键字、是否已开通账号；
2. 选择附加角色；
3. 预览：命中人数、已拥有该角色人数、将新增人数；
4. 执行：分批 500 条，`INSERT ... ON DUPLICATE KEY UPDATE` 幂等；
5. 返回：成功/跳过/失败清单，写审计日志。

### 方式二：Excel 批量（补）

模板列：`person_no`、`角色编码`、`是否默认`。
逐行校验：人员存在、账号存在、角色合法、重复行；分批导入并回执失败原因。

### 方式三：导入自动（默认主角色）

人员导入时只自动赋主角色；附加角色不自动赋，避免误授权。

### 性能

- 超过 500 条走异步任务表，前端轮询进度；
- 唯一键 `(user_id, role, school_id)` 保证幂等；
- 禁止一次性加载全表，按 id 游标分页。

## 七、页面改造

### 7.1 人员管理

字段：

```
工号/学号(person_no) | 姓名 | 手机号 | 类型 | 部门/班级 | 状态
```

- 工号/学号必填、唯一；
- 手机号必填；
- 部门/班级按类型显示：教职工显示部门，学生显示班级；
- 列表可附“账号状态”标识（已开通/未开通）；
- 行操作：编辑、分配账号/角色、停用；
- 顶部：新增人员、导入、批量分配角色；
- 停用确认框：有待办时展示数量并禁止提交。

### 7.2 账号管理

字段：

```
工号/学号 | 姓名 | 手机号 | 角色 | 状态
```

- 工号/学号：来自人员，只读，可为空（管理员/门卫）；
- 姓名：关联人员姓名；无人员档案时手工维护；
- 手机号：**账号登录手机号**，可编辑，校验全局唯一；修改不影响人员档案；
- 角色：身份角色置灰，附加角色可增删；
- 状态：启用/停用；
- 搜索：工号/学号、姓名、手机号；
- 详情：显示关联人员、openid 绑定状态、最后登录时间。

## 八、迁移与上线步骤

1. 执行 `026-person-no.sql`（新增字段/索引/映射/回填）；
2. 部署后端：主角色保护、类型同步、停用校验、账号接口；
3. 部署前端：人员/账号页改造、角色切换器；
4. 数据核对：
   - 在职人员是否都有 person_no；
   - person_no 与账号是否一一对应；
   - 每人 IDENTITY 角色是否唯一；
   - 账号手机号是否唯一；
5. 灰度：先小范围验证新增/停用/恢复，再全量。

| 12 | 停用有未处理任务的账号 | 400，阻止 |
| 13 | 删除主角色 | 400，提示由人员类型决定 |
| 14 | 添加附加角色（部门经办人） | 成功，可切换角色 |
| 15 | 批量分配 1000 人 | 幂等、分批、可查结果 |
| 16 | 无 person_no 新增人员 | 400，工号/学号必填 |

---

## 十、暂不做

- 角色互斥矩阵（保留运行时“申请人≠审批人”校验）；
- 短信平台对接（先用手机号+密码登录，微信绑定后续接）；
- 学号/工号登录（登录仍用账号手机号或微信 openid）；
- 人员类型自定义扩展（固定 7 种）；
- 手机号变更短信二次确认（先由管理员直接改）。

---

## 十一、风险与注意

1. 存量人员可能缺 `person_no`，迁移后需中台补齐，否则无法开通账号；
2. 历史账号按手机号回填 `person_no`，重复手机号/一号多人需人工清洗；
3. 账号手机号与人员手机号分离后，需明确“账号手机号由谁维护”，避免两边都改；
4. 自动建账号会产生大量默认密码账号，上线后应要求首次登录改密或接入统一身份；
5. 待办阻止停用会影响管理员操作效率，需要配套“转交待办”功能；
6. 微信登录能否一键取手机号取决于载体（小程序/企业微信/运营商/公众号），公众号 H5 需短信绑定兜底。
