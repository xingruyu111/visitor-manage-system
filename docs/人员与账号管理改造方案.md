# 人员管理与账号管理改造方案

> 依据：采购文档附件1 用户管理模块、附件2 第3/4项。
> 目标：人员类型作为审批身份与主角色来源，角色决定登录/功能权限；人员与账号一对一，按 `person_no` 关联。
> 本文是改造设计，不含代码实现。

---

## 一、已确认的设计决策

| 决策 | 结论 |
|---|---|
| 人员类型的作用 | 审批身份依据；导入/新增时按类型生成**主角色**；不直接参与权限判断 |
| 角色的作用 | 登录权限、功能权限、菜单/接口访问 |
| 人员与账号 | 一人一账号；按 `person_no`（统一学号/工号）关联 |
| 手机号 | **必填**，作为登录凭证 |
| 主角色 | 由人员类型生成，**不可删除、不可单独停用**；只能随人员类型变更或人员停用而变化 |
| 修改人员类型 | 主角色同步替换；附加角色保持不变 |
| 删除人员 | 人员软删 + 账号停用 + 角色停用，数据不删 |
| 重新添加人员 | 按 `person_no` 找回原人员和原账号，恢复启用及历史数据 |
| 账号停用 | 系统管理员停用后立即无法登录（含已签发 token） |
| 停用前待办 | **阻止停用**：存在未处理审批任务时不允许停用，需先转交 |
| 角色冲突 | 本期不做互斥矩阵，后续按需增加 |
| 角色切换 | 支持一人多角色，应用内切换；默认角色 `is_default` |

### 人员类型（7 种）

| 编码 | 名称 | 主角色 |
|---|---|---|
| 1 | 教职工 | 教职工（5） |
| 2 | 学生 | 学生（6） |
| 3 | 校内商户 | 校内商户（7） |
| 4 | 食堂人员 | 食堂人员（8） |
| 5 | 附属学校教职工 | 教职工（5） |
| 6 | 附属学校学生 | 学生（6） |
| 7 | 校友 | 校友（9） |

### 角色（10 种）

| 编码 | 名称 | 来源 |
|---|---|---|
| 1 | 系统管理员 | 独立账号，无人员类型 |
| 2 | 保卫处管理员 | 附加角色/独立账号 |
| 3 | 门卫 | 附加角色/独立账号 |
| 4 | 访客 | 微信注册，不建人员档案 |
| 5 | 教职工 | 主角色（教职工/附属教职工） |
| 6 | 学生 | 主角色（学生/附属学生） |
| 7 | 校内商户 | 主角色 |
| 8 | 食堂人员 | 主角色 |
| 9 | 校友 | 主角色 |
| 11 | 二级学院/机关部处经办人 | 附加角色 |

> 说明：类型与角色不是一一对应。主角色只有 5 种；保卫处管理员、门卫、部门经办人、系统管理员、访客没有人员类型。

## 二、现状与差距

| 现状 | 问题 | 改造 |
|---|---|---|
| `vst_staff` 有 `job_no`、`student_no` 两个字段 | 学号/工号不统一 | 新增 `person_no`，统一写入；旧字段保留兼容 |
| 人员与账号仅靠手机号匹配 | 改手机号/重号会断开关联 | 新增 `vst_staff_account` 一对一映射 |
| `vst_user_role` 无来源标记 | 分不清主角色和附加角色 | 增加 `source`（IDENTITY/MANUAL） |
| 账号页 `assignRole` 是“替换唯一角色” | 不能真正多角色 | 改为角色增删接口 |
| 人员类型变更不更新角色 | 身份与权限不一致 | 事务内替换 IDENTITY 角色 |
| 人员停用只停角色，不改 `user.status` | 账号状态不彻底 | 人员停用同时 `user.status=0` |
| 账号停用会级联停用全部角色 | 重新启用后角色恢复困难 | 账号停用只改 `user.status`，角色保持；人员停用才级联 |
| 停用前不检查待办 | 审批任务卡死 | 待办存在则拒绝停用 |
| 新增人员不建账号 | 一人一号需要手工补 | 人员新增/导入自动开通账号并赋主角色 |
| 角色切换只有后端请求头 | 前端无入口 | 增加角色列表接口与切换器 |

## 三、数据模型改造

### 3.1 人员表

```sql
ALTER TABLE vst_staff ADD COLUMN person_no VARCHAR(64) NULL COMMENT '统一学号/工号' AFTER phone;
CREATE UNIQUE INDEX uk_staff_person_no ON vst_staff (school_id, person_no);
```

规则：

- `person_no` 为人员唯一业务编号；教职工/学生/附属学校人员**必填**；商户/食堂/校友可空，空时用手机号兜底；
- `job_no`、`student_no` 保留用于展示和旧数据兼容，导入时同步写入；
- 手机号必填，新增/导入校验非空。

### 3.2 人员-账号映射

```sql
CREATE TABLE vst_staff_account (
  id         BIGINT NOT NULL AUTO_INCREMENT,
  staff_id   BIGINT NOT NULL,
  user_id    BIGINT NOT NULL,
  school_id  BIGINT NULL,
  created_at DATETIME NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_staff_account_staff (staff_id),
  UNIQUE KEY uk_staff_account_user (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='人员账号关联';
```

### 3.3 角色来源标记

```sql
ALTER TABLE vst_user_role
  ADD COLUMN source VARCHAR(16) NOT NULL DEFAULT 'MANUAL' COMMENT 'IDENTITY主角色/MANUAL附加角色';
```

约定：

- 每人最多一条 `source=IDENTITY`；
- 人员类型变更时删旧主角色、插新主角色；
- `source=IDENTITY` 的记录禁止删除/单独停用；
- 附加角色可增删，不影响主角色。

### 3.4 类型-角色映射表

```sql
CREATE TABLE vst_person_type_role (
  person_type TINYINT NOT NULL,
  role        TINYINT NOT NULL,
  description VARCHAR(64) NULL,
  updated_at  DATETIME NULL,
  PRIMARY KEY (person_type)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='人员类型默认角色';

INSERT INTO vst_person_type_role VALUES
 (1,5,'教职工',NOW()),(2,6,'学生',NOW()),(3,7,'校内商户',NOW()),
 (4,8,'食堂人员',NOW()),(5,5,'附属教职工',NOW()),(6,6,'附属学生',NOW()),
 (7,9,'校友',NOW());
```

### 3.5 数据迁移（026）

1. 回填 `person_no = COALESCE(job_no, student_no)`；
2. 按手机号匹配人员与账号，写入 `vst_staff_account`；
3. 对已有关联账号：若角色等于人员类型映射角色，置 `source=IDENTITY`、`is_default=1`；否则补插一条主角色；
4. 其余角色统一 `source=MANUAL`；
5. 初始化 `vst_person_type_role`。

## 四、核心业务规则

### 4.1 新增/导入人员

流程：

```
校验 person_no 唯一、手机号必填
  → 按 person_no 找已有人员
      → 找到停用人员：恢复人员，复用原账号（不新建）
      → 未找到：新增人员
  → 按手机号找账号
      → 有：绑定 staff_account
      → 无：创建账号（默认密码 123456）
  → 按类型写入/修正 IDENTITY 主角色
  → 返回人员 + 账号状态
```

约束：

- 手机号已属于其他人（不同 person_no）→ 拒绝，提示冲突；
- 一个账号只能绑定一个人员；
- 已有账号的附加角色不因导入被清空，只保证主角色存在。

### 4.2 修改人员类型

事务内：

1. 记录旧类型、旧主角色；
2. 更新人员类型；
3. 删除旧 `IDENTITY` 角色；
4. 插入新 `IDENTITY` 角色（若同一角色可复用，仅更新）；
5. 新主角色设为默认；
6. 附加角色不动；
7. 写审计日志。

### 4.3 删除人员（软删）

前置检查：

- 统计 `vst_approval_task` 中 `assignee_id=该账号 且 status=PENDING`；
- 大于 0 → 拒绝，返回“还有 N 条待审批，请先转交”。

通过后：

1. `staff.status=0`；
2. `user.status=0`；
3. 该用户全部角色 `status=0`；
4. 保留 `staff_account`、历史预约、审批记录。

### 4.4 重新添加人员

- 按 `person_no` 匹配停用人员（其次手机号）；
- 恢复同一 `staff.id`、同一 `user.id`；
- `staff.status=1`、`user.status=1`、角色 `status=1`；
- 若主角色缺失或类型已变，按当前类型重建；
- 历史审批记录、预约记录仍指向原账号，不需迁移。

### 4.5 停用/启用账号（系统管理员）

- 停用前同样检查待办，有则阻止；
- 停用：`user.status=0`，**不级联角色**；
- 启用：`user.status=1`，角色沿用停用前状态；
- 已签发 token：`AuthInterceptor` 每次请求校验 `user.status`，停用后立即 403，无需等 token 过期。

### 4.6 主角色保护

接口层：

- 删除角色：若 `source=IDENTITY` → 400“该角色由人员类型决定，请修改人员类型或停用人员”；
- 停用角色：同上；
- 修改角色：不允许把 IDENTITY 改成其他角色，只能走“修改人员类型”。

### 4.7 多角色与切换

- 登录返回 `currentRole` 和角色列表；
- 前端顶部角色切换器；
- 切换时请求头带 `X-Current-Role`，后端校验该角色属于当前用户；
- 切换写审计日志；
- 默认角色取 `is_default=1` 的主角色；没有则取第一个启用角色。

### 4.8 审批链

- 被访人审批链按 **`staff.person_type`** 判断，与当前激活角色无关；
- 审批人处理任务时仍要求账号启用、角色启用、任务分配给本人；
- 保留运行时校验：申请人不能审批自己的预约；
- 角色互斥矩阵本期不做。

## 六、批量分配角色

场景：中台同步几万人后，需要批量授予“部门经办人”等附加角色。

### 方式一：规则批量（主）

1. 选择条件：人员类型、部门、班级、关键字、是否已开通账号；
2. 选择附加角色；
3. 预览：命中人数、已拥有该角色人数、将新增人数；
4. 执行：分批 500 条，`INSERT ... ON DUPLICATE KEY UPDATE` 幂等；
5. 返回：成功/跳过/失败清单，写审计日志。

### 方式二：Excel 批量（补）

模板列：`person_no`、`手机号`、`角色编码`、`是否默认`。
逐行校验：人员存在、账号存在、角色合法、重复行；分批导入并回执失败原因。

### 方式三：导入自动（默认主角色）

人员导入时只自动赋主角色；附加角色不自动赋，避免误授权。

### 性能

- 超过 500 条走异步任务表，前端轮询进度；
- 唯一键 `(user_id, role, school_id)` 保证幂等；
- 禁止一次性加载全表，按 id 游标分页。

- 停用确认框：有待办时提示先转交；
- 角色切换入口放到右上角用户菜单（Web/H5）。

## 八、迁移与上线步骤

1. 执行 `026-staff-account.sql`（新增字段/表/索引/映射/回填）；
2. 部署后端：主角色保护、类型同步、停用校验、账号接口；
3. 部署前端：人员/账号页改造、角色切换器；
4. 数据核对：
   - 在职人员有账号比例；
   - 每人 IDENTITY 角色是否唯一；
   - staff_account 一对一是否冲突；
5. 灰度：先小范围人员验证新增/停用/恢复，再全量。

## 十、暂不做

- 角色互斥矩阵（先保留运行时“申请人≠审批人”校验）；
- 短信/微信激活账号（当前仍默认密码 123456，后续可加首次登录改密）；
- 学号/工号登录（当前登录仍用手机号）；
- 人员类型自定义扩展（固定 7 种）。

---

## 十一、风险与注意

1. 历史数据中可能存在“同一手机号多人员”，迁移时需先清洗；
2. 存量人员可能缺 `person_no`，只能先回填空值，后续由中台补齐；
3. 账号停用不再级联角色，需确认“停用账号但角色仍启用”符合安全要求（登录已被 user.status 拦截）；
4. 自动建账号会产生大量默认密码账号，上线后应要求首次登录改密或接入统一身份；
5. 待办阻止停用会影响管理员操作效率，需要配套“转交待办”功能，否则无法停用离职人员。
