# 辅导员管理设计与实现文档

> 版本：v1.0  
> 范围：Web 管理端「人员管理」新增辅导员管理；学生被访预约自动解析辅导员  
> 依赖：组织树（`vst_org`）、人员（`vst_staff`）、账号角色（`vst_user` / `vst_user_role`）、审批引擎（`AssigneeResolver`）

---

## 1. 背景与目标

文档要求：

> 被访人是本校学生：访客提交预约 → 学生（被访人）审批 → 辅导员二次审批；其中学生和辅导员的对应管理关系，访客系统从数据中台进行获取、存储、展示、更新。

现状只有零散字段：

- `vst_staff.counselor_id`：学生个人指定辅导员；
- `vst_class.counselor_id`：班级指定辅导员；
- 审批节点 `COUNSELOR` 通过 `AssigneeResolver` 读取上述字段。

问题：

1. 没有界面维护辅导员与学生/组织的对应关系；
2. 按组织批量关联无法表达；
3. 组织下新增学生不会自动继承；
4. 辅导员账号如果没有 `COUNSELOR` 角色，H5 看不到审批入口。

本功能目标：

- 在「人员管理」内新增“辅导员管理”；
- 选择一个已存在人员作为辅导员，再选择一个组织；
- 该组织及其所有下级组织内的人员自动与该辅导员关联；
- 学生被访预约进入二级审批时，按该关联解析辅导员；
- 组织新增人员、人员调动后无需重新维护。

---

## 2. 方案选型

### 2.1 方案 A：批量写 `staff.counselor_id`（不采用）

给组织下每个人员直接写 `counselor_id`。

缺点：

- 新增人员不继承，必须定时补；
- 人员调组织后旧关联残留；
- 组织层级调整后需要全量重算；
- 无法表达“整个组织由某辅导员负责”。

### 2.2 方案 B：组织—辅导员映射表（采用）

新增 `vst_counselor_org`：

- 一行表示“某辅导员负责某组织及其子树”；
- 审批时按学生所在组织向上查找最近映射；
- 新增/调动人员自动生效；
- 保留 `staff.counselor_id` 和 `class.counselor_id` 作为兼容兜底。

采用方案 B。

## 3. 数据模型

### 3.1 新表 `vst_counselor_org`

```sql
CREATE TABLE vst_counselor_org (
  id                BIGINT NOT NULL AUTO_INCREMENT,
  school_id         BIGINT NOT NULL DEFAULT 1,
  counselor_staff_id BIGINT NOT NULL COMMENT '辅导员：vst_staff.id',
  org_id            BIGINT NOT NULL COMMENT '负责组织：vst_org.id，含所有下级',
  created_by        BIGINT,
  created_at        DATETIME,
  updated_at        DATETIME,
  PRIMARY KEY (id),
  UNIQUE KEY uk_counselor_org (school_id, org_id),
  KEY idx_counselor_staff (counselor_staff_id),
  KEY idx_counselor_school (school_id)
) COMMENT '辅导员与组织关联';
```

设计说明：

| 项 | 规则 |
|---|---|
| 一个组织 | 只能配置一个辅导员（唯一键） |
| 一个辅导员 | 可以负责多个组织 |
| 父子组织 | 可以分别配置不同辅导员；离学生最近的组织优先 |
| 同一组织重复新增 | 返回 409「该组织已配置辅导员」 |
| 删除组织 | 若存在映射，阻止删除并提示先移除辅导员 |
| 删除辅导员人员 | 级联删除其映射，并回收自动授予的辅导员角色（见 3.3） |

### 3.2 解析优先级

学生 `staff`：

1. `staff.counselor_id` 非空 → 直接使用（个人指定优先）；
2. 从学生 `org_id` 开始，沿组织祖先链向上找 `vst_counselor_org`，取**最近一级**映射；
3. 回退 `vst_class.counselor_id`；
4. 仍为空 → 审批任务走管理员兜底（沿用现有逻辑）。

组织祖先链示例：

```
24软件1（学生所在） → 24级 → 人工智能学院
```

若只有“人工智能学院”配置了辅导员，则 24软件1 学生解析到该辅导员；若“24级”也配置了另一人，则 24软件1 学生优先“24级”的辅导员。

### 3.3 辅导员角色授予（仅限本功能）

辅导员角色**只能通过辅导员管理新增映射时授予**，不能在账号管理里手工分配：

- 账号管理的“添加角色”下拉不展示辅导员；
- 后端 `UserAdminService.addRole` 对 `COUNSELOR` 返回 400：「辅导员角色只能通过辅导员管理授予」；
- 选择人员后：
  - 无账号 → 自动建号（手机号必填）；
  - 无 `COUNSELOR` 角色 → 自动追加，`source = AUTO_COUNSELOR`；
  - 已有 `COUNSELOR` 角色（历史数据）→ 复用，不重复添加。
- 删除映射时：
  - 该人员还有其他组织映射 → 保留角色；
  - 没有其他映射且角色来源是 `AUTO_COUNSELOR` → 回收角色；
  - 手工/历史来源的角色不自动回收（避免误删）。
- 一个辅导员负责多个组织时，只授予一次角色。

> 迁移时可将历史手工授予的 `COUNSELOR` 角色保留，但后续新增只能走辅导员管理。

### 3.4 附属学生不走辅导员

附属学生预约仍按文档“填写班主任工号”处理：

- 不使用组织/班级上的 `head_teacher_id` 关联；
- 访客在 H5 填写工号，后端按 `vst_staff.job_no` 找到教师账号；
- 该教师直接作为审批人（`assigneeHint`），**不再生成辅导员二级节点**；
- 对应流程 `VISIT_AFFILIATED_STUDENT` 只保留一个审批节点。

> `AssigneeResolver` 中的 `HEAD_TEACHER` 仅作为“按工号指定的教师”占位类型使用，不再读取班级班主任字段。

### 3.5 索引与数据量

单校规模，映射表预计几十到几百行；查询按 `school_id + org_id` 命中唯一索引，无需分页优化。

## 4. 接口设计

统一前缀：`/web/admin/counselors`  
权限：`SYSTEM_ADMIN`、`SECURITY_ADMIN`（与人员管理一致）。

### 4.1 分页列表

```http
GET /web/admin/counselors?keyword=&page=1&size=20
```

返回：

```json
{
  "total": 3,
  "records": [
    {
      "id": 1,
      "counselorStaffId": 10,
      "counselorName": "张老师",
      "counselorPersonNo": "T001",
      "counselorPhone": "139...",
      "orgId": 21,
      "orgName": "人工智能学院/24级",
      "studentCount": 86,
      "createdAt": "2026-11-10 10:00:00"
    }
  ]
}
```

`studentCount`：该组织子树内 `person_type=2`（学生）且未删除的人数，用于确认覆盖范围。

### 4.2 查询可选人员

```http
GET /web/admin/counselors/candidates?keyword=张
```

只返回：

- `person_type in (1,5)`（教职工/附属教职工）；
- `status=1`、`is_deleted=0`；
- 有手机号（能建账号）。

返回 `id/name/personNo/phone/orgName`。

> 也可以复用 `/web/admin/staff`，但新增候选接口可以限制人员类型，避免误选学生/商户。

### 4.3 新增关联

```http
POST /web/admin/counselors
Content-Type: application/json

{
  "counselorStaffId": 10,
  "orgId": 21
}
```

校验：

1. 人员存在、未删除、类型合法；
2. 组织存在；
3. 该组织未配置辅导员；
4. 人员有手机号；
5. 账号可用，必要时自动建号；
6. 自动补 `COUNSELOR` 角色。

返回创建后的映射。

错误码：

| 场景 | code | message |
|---|---|---|
| 组织已配置 | 409 | 该组织已配置辅导员 |
| 人员类型不符 | 400 | 只能选择教职工担任辅导员 |
| 无手机号 | 400 | 该人员没有手机号，无法创建审批账号 |
| 组织不存在 | 400 | 组织不存在 |

### 4.4 删除关联

```http
DELETE /web/admin/counselors/{id}
```

- 删除映射；
- 若该人员已无其他映射，回收自动授予的 `COUNSELOR` 角色；
- 不影响历史审批任务。

### 4.5 修改负责组织（可选）

```http
PUT /web/admin/counselors/{id}
{ "orgId": 22 }
```

等价于删除旧映射 + 新增新映射，需重新做唯一校验。

### 4.6 覆盖人员预览（可选）

```http
GET /web/admin/counselors/preview?orgId=21
```

返回：

```json
{ "studentCount": 86, "staffCount": 102 }
```

用于新增弹窗中提示“该组织下共有 86 名学生将关联此辅导员”。

### 5.3 组织子树判断

复用组织表 `ancestors`：

```sql
SELECT s.* FROM vst_staff s
JOIN vst_org o ON o.id = s.org_id
WHERE o.id = #{orgId}
   OR FIND_IN_SET(#{orgId}, o.ancestors)
```

`studentCount` 在此基础上加 `s.person_type=2 AND s.is_deleted=0`。

### 5.4 审批解析改造

`AssigneeResolver` 注入 `CounselorOrgMapper`、`OrgMapper`：

```java
private Long counselorIdOf(Long studentId) {
    Staff student = staffId(studentId);
    if (student == null) return null;

    // 1. 个人指定
    if (student.getCounselorId() != null) return student.getCounselorId();

    // 2. 组织最近映射
    Long byOrg = counselorByOrg(student.getOrgId());
    if (byOrg != null) return byOrg;

    // 3. 班级兜底
    SchoolClass clazz = student.getClassId() == null ? null : classMapper.selectById(student.getClassId());
    return clazz == null ? null : clazz.getCounselorId();
}

private Long counselorByOrg(Long orgId) {
    if (orgId == null) return null;
    Org org = orgMapper.selectById(orgId);
    List<Long> chain = new ArrayList<>();
    while (org != null) {
        chain.add(org.getId());
        org = org.getParentId() == null ? null : orgMapper.selectById(org.getParentId());
    }
    for (Long id : chain) {
        CounselorOrg mapping = counselorOrgMapper.selectOne(
            new LambdaQueryWrapper<CounselorOrg>()
                .eq(CounselorOrg::getOrgId, id)
                .last("LIMIT 1"));
        if (mapping != null) return mapping.getCounselorStaffId();
    }
    return null;
}
```

只对 `person_type=2`（本校学生）生效；附属学生仍按 `HEAD_TEACHER` 流程，不走辅导员。

### 5.5 账号与角色

新增映射时：

```java
User user = ensureAccount(staff);          // 复用人员模块逻辑
ensureRole(user.getId(), RoleEnum.COUNSELOR, "AUTO_COUNSELOR");
```

删除映射时：

```java
if (countOtherMappings(staffId) == 0) {
    removeRoleIfSourceAuto(userId, RoleEnum.COUNSELOR);
}
```

- `COUNSELOR_ORG_DELETE`：辅导员、组织；

## 7. 与审批流程的衔接

### 7.1 本校学生（两级）

1. 访客选择被访人（学生）→ 启动 `VISIT_STUDENT`；
2. 节点 1 `TARGET`：学生本人；
3. 节点 2 `COUNSELOR`：
   - `AssigneeResolver` 按第 3.2 节解析辅导员；
   - 解析到用户 → 生成待办；
   - 解析不到 → 保持现状（管理员兜底/流程异常提示）。
4. 辅导员在 H5「我的待办」看到任务，通过/驳回；
5. 两级通过后预约生效。

### 7.2 附属学生（单级，按工号）

1. 访客选择附属学生作为被访人；
2. H5 必填“班主任工号”；
3. 后端按 `vst_staff.job_no` 找到教师，并解析其账号；
4. 流程只保留一个节点：`assignee = HEAD_TEACHER`，但实际审批人取 `assigneeHint`（工号对应教师）；
5. 不再生成 `COUNSELOR` 节点，不读取班级 `head_teacher_id`。

现有 `VISIT_AFFILIATED_STUDENT` 定义需要同步调整：

```json
{
  "code": "VISIT_AFFILIATED_STUDENT",
  "name": "实验学校学生访客流程",
  "timeoutHours": 24,
  "nodes": [
    { "seq": 1, "name": "工号对应教师审批", "assignee": "HEAD_TEACHER" }
  ]
}
```

迁移时更新 `vst_approval_flow.definition_json` 并递增 `version`；已发布流程需重新发布或直接更新启用记录。

### 7.3 其他

- 学生转专业/换班：组织映射自动生效；个人 `counselor_id` 非空时仍优先个人指定。
- 附属学生不参与辅导员解析，即使组织配置了辅导员也不生成辅导员任务。

## 8. 边界与异常

| 场景 | 处理 |
|---|---|
| 组织下无学生 | 允许配置，覆盖数 0 |
| 同一组织重复配置 | 409，提示先移除 |
| 辅导员停用 | 无待办任务时允许停用；映射保留，解析时跳过停用账号，继续向上级组织查找 |
| 辅导员调离 | 人员删除时级联删除映射；建议删除前提示影响组织数 |
| 组织被删除 | 有映射时阻止删除 |
| 组织层级调整 | 映射跟随组织 ID，子树关系自动更新 |
| 一个学生匹配多个映射 | 最近祖先优先；同层唯一键保证不冲突 |
| 学生无组织 | 回退班级/个人辅导员，仍无则管理员兜底 |
| 一个辅导员负责多个组织 | 允许，角色只授予一次 |

- [ ] 附属学生流程只有工号对应教师一个审批节点；
- [ ] 相关单测、集成测试、E2E 通过。

## 13. 已确认决策与待确认

### 已确认

1. 辅导员只允许“教职工/附属教职工”；
2. 一个组织只能配置一个辅导员；
3. 辅导员角色只能通过辅导员管理授予，账号管理不能手工分配；
4. 删除映射时回收本功能自动授予的 `COUNSELOR` 角色；
5. 附属学生按工号指定教师审批，只保留一个审批节点，不使用班级班主任关联。
6. 辅导员没有待处理审批任务时允许停用；停用后保留映射，审批解析跳过该辅导员。
