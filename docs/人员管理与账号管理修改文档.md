# 人员管理与账号管理修改文档

> 范围：只改人员管理、账号管理及其关联规则。
> 依据：采购文档附件1 用户管理模块、附件2 第3/4项。
> 结论：人员与账号按 `person_no`（工号/学号）关联；人员类型生成主角色；角色决定权限；手机号两边独立维护。

---

## 一、页面字段

### 1.1 人员管理

列表字段：

| 工号/学号 | 姓名 | 手机号 | 类型 | 部门/班级 | 职务（备注） | 状态 |
|---|---|---|---|---|---|---|

编辑表单：

| 字段 | 必填 | 说明 |
|---|---|---|
| 工号/学号 `person_no` | 是 | 唯一；教职工/学生由中台提供，商户/食堂/校友由学校分配 |
| 姓名 | 是 | |
| 手机号 | 是 | 人员联系电话，可与账号手机号不同 |
| 类型 | 是 | 教职工/学生/校内商户/食堂人员/附属学校教职工/附属学校学生/校友 |
| 部门/班级 `org_id` | 是 | 从组织架构树选择一个节点（学院/年级/班级均可） |
| 职务 | 否 | 自由文本备注，仅展示，不参与业务 |
| 状态 | 是 | 在职/停用 |

行操作：编辑、分配账号、停用。

顶部操作：新增人员、导入人员、批量分配角色。

### 1.2 账号管理

列表字段：

| 工号/学号 | 姓名 | 手机号 | 角色 | 状态 |
|---|---|---|---|---|

- 工号/学号：来自关联人员，只读；独立账号可为空；
- 姓名：关联人员姓名；无人员档案时手工维护；
- 手机号：**账号登录手机号**，可编辑，全局唯一；
- 角色：主角色（身份角色）置灰不可删；附加角色可增删；
- 状态：启用/停用。

行操作：停用/启用、添加附加角色、移除附加角色、重置密码、修改账号手机号。

顶部操作：新增独立账号（无人员档案时使用）、批量分配角色。

## 二、关联规则

### 2.1 人员与账号

- 关联键：`person_no`；
- 人员表 `person_no` 唯一；
- 账号表增加 `person_no`，可空、唯一；
- 一个人员最多一个账号，一个账号最多关联一个人员；
- 查询：`staff.person_no = user.person_no`。

### 2.2 两类账号

| 类型 | person_no | 角色 |
|---|---|---|
| 人员账号（教师/学生/保卫处人员等） | 有值 | 主角色由人员类型生成 + 附加角色 |
| 独立账号（保安公司人员、系统管理员等） | 可空 | 全部角色手工分配，无主角色保护 |

管理员、门卫通常是给**已有账号分配附加角色**，不需要重新建人员或账号。

### 2.3 两个手机号

| 手机号 | 归属 | 用途 | 变更影响 |
|---|---|---|---|
| 人员手机号 | 人员档案 | 联系方式、开通账号时的初始值 | 不影响账号登录 |
| 账号手机号 | 账号 | 登录、微信绑定、密码找回 | 不影响人员档案 |

规则：

- 新建账号时，账号手机号默认取人员手机号；
- 之后两边独立，人员换号不改账号，账号换号不改人员；
- 账号手机号全局唯一；
- 微信登录按账号手机号匹配，人员手机号不参与。

## 三、角色规则

### 3.1 主角色与附加角色

- 人员类型 → 主角色，写入 `user_role` 且 `source=IDENTITY`；
- 主角色不可删除、不可单独停用；
- 管理员、门卫、部门经办人、辅导员等为附加角色（`source=MANUAL`），可增删；
- 独立账号没有主角色，所有角色均可增删。

### 3.2 类型与主角色映射

| 人员类型 | 主角色 |
|---|---|
| 教职工、附属学校教职工 | 教职工（5） |
| 学生、附属学校学生 | 学生（6） |
| 校内商户 | 校内商户（7） |
| 食堂人员 | 食堂人员（8） |
| 校友 | 校友（9） |

### 3.3 修改人员类型

事务内：

1. 更新人员类型；
2. 删除旧 `IDENTITY` 角色；
3. 插入新 `IDENTITY` 角色；
4. 新主角色设为默认；
5. 附加角色保持不变；
6. 写审计日志。

### 3.4 新增辅导员角色

- 文档中辅导员是学生审批的二级审批人，需要登录系统，因此增加角色 **辅导员（12）**；
- 辅导员作为附加角色授予，人员 `org_id` 挂在学院节点；
- 班主任不建角色：仍按班级节点的班主任字段/工号定位；
- 年级主任文档未提及，不建角色。

### 3.5 审批定位

| 场景 | 审批人来源 |
|---|---|
| 学生预约 | 学生本人 → 辅导员（角色=辅导员，且 `org_id` 为所在班级的上级学院节点） |
| 附属学生预约 | 按班级节点的班主任 / 填写的班主任工号 |
| 教职工、商户、食堂、附属教职工 | 被访人本人 |

### 3.6 多角色与切换

- 一个账号可多角色；
- 登录返回角色列表和默认角色；
- 前端顶部角色切换，请求头带 `X-Current-Role`；
- 后端校验角色属于当前账号；
- 切换写审计日志；
- 角色冲突矩阵本期不做。

## 四、生命周期

### 4.1 新增/导入人员

```
校验 person_no 唯一、手机号必填
  → 按 person_no 查人员
      找到停用人员：恢复人员，复用原账号
      未找到：新增人员
  → 按 person_no 查账号
      有：关联，不覆盖账号手机号
      无：创建账号，账号手机号=人员手机号，默认密码 123456
  → 按人员类型写入主角色
```

约束：

- `person_no` 重复 → 拒绝；
- 账号手机号已存在 → 拒绝，提示冲突；
- 已有账号的附加角色不被清空；
- 人员手机号变化不自动改账号手机号。

### 4.2 删除人员（停用）

前置检查：

- 查询该账号名下 `status=PENDING` 的审批任务；
- 有任务 → **拒绝停用**，提示“还有 N 条待审批，请先转交”。

通过后：

1. `staff.status=0`；
2. `user.status=0`；
3. 该用户全部角色 `status=0`；
4. 保留人员、账号、角色、历史记录。

### 4.3 重新添加人员

- 按 `person_no` 找回原人员和账号；
- 恢复 `staff.status=1`、`user.status=1`、角色 `status=1`；
- 账号手机号保持停用前的值，不用人员手机号覆盖；
- 主角色缺失或类型已变时，按当前类型重建。

### 4.4 停用/启用账号

- 停用前同样检查待办，有则阻止；
- 停用只改 `user.status=0`，不级联角色；
- 启用只改 `user.status=1`，角色沿用停用前状态；
- 已登录 token 立即失效：拦截器每次请求校验 `user.status`。

### 4.5 主角色保护

- 删除主角色 → 400“该角色由人员类型决定，请修改人员类型或停用人员”；
- 停用主角色 → 同上；
- 修改主角色只能通过修改人员类型。

## 五、数据模型

### 5.1 人员表

```sql
ALTER TABLE vst_staff ADD COLUMN person_no VARCHAR(64) NULL COMMENT '工号/学号';
ALTER TABLE vst_staff ADD COLUMN org_id BIGINT NULL COMMENT '组织节点';
CREATE UNIQUE INDEX uk_staff_person_no ON vst_staff (person_no);
```

### 5.2 账号表

```sql
ALTER TABLE vst_user ADD COLUMN person_no VARCHAR(64) NULL COMMENT '关联人员工号/学号';
CREATE UNIQUE INDEX uk_user_person_no ON vst_user (person_no);
```

### 5.3 角色来源

```sql
ALTER TABLE vst_user_role
  ADD COLUMN source VARCHAR(16) NOT NULL DEFAULT 'MANUAL' COMMENT 'IDENTITY/MANUAL';
```

### 5.4 组织表

单校部署，`school_id` 固定为 1，组织表最小字段：

```sql
CREATE TABLE vst_org (
  id          BIGINT NOT NULL AUTO_INCREMENT,
  parent_id   BIGINT NULL,
  name        VARCHAR(128) NOT NULL,
  ancestors   VARCHAR(512) NULL,
  level       INT DEFAULT 1,
  sort_order  INT DEFAULT 0,
  head_teacher_id BIGINT NULL COMMENT '班主任（班级节点）',
  external_id VARCHAR(64) NULL COMMENT '数据中台编码',
  status      TINYINT DEFAULT 1,
  created_at  DATETIME NULL,
  updated_at  DATETIME NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_org_external (external_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='组织架构';
```

说明：

- 不设 `node_type`，学院/年级/班级由层级表达；
- 班级并入组织树，原 `vst_class` 的班主任迁到 `head_teacher_id`；
- `external_id` 保留，数据中台同步按编码幂等更新；
- 人员 `org_id` 指向任意层级节点。

### 5.5 辅导员角色

角色由代码枚举 `RoleEnum` 管理，没有角色表。

在 `RoleEnum` 中新增：

```java
COUNSELOR(12, "辅导员")
```

同步调整：

- `/web/common/roles` 返回该角色；
- 账号页允许分配/移除；
- 审批页允许辅导员访问；
- 数据迁移无需建表。

## 七、批量分配角色

给已有账号批量加附加角色（如部门经办人、辅导员）：

1. 筛选：人员类型、组织节点（含子节点）、关键字、是否已开通账号；
2. 选择附加角色；
3. 预览：命中人数、已有该角色人数、将新增人数；
4. 执行：按 500 条分批，`INSERT ... ON DUPLICATE KEY UPDATE`；
5. 返回成功/跳过/失败明细，写审计日志。

导入人员时只自动赋主角色，不自动赋附加角色。

## 八、迁移步骤

1. 建组织树：部门迁入，班级作为叶子节点挂到年级/学院下，回填 `head_teacher_id`；
2. 人员：
   - `person_no = COALESCE(job_no, student_no)`；
   - `org_id = class_id` 映射的班级节点，或 `dept_id` 映射的部门节点；
3. 账号：
   - 按 `phone` 匹配人员，回填 `person_no`；
   - 重复手机号/一人多账号列清单人工处理；
4. 角色：
   - 角色等于人员类型映射角色 → `source=IDENTITY`、`is_default=1`；
   - 其余 → `source=MANUAL`；
5. 初始化辅导员角色；
6. 加唯一索引前清理重复数据。

## 十、暂不做

- 角色互斥矩阵；
- 班主任、年级主任建角色；
- 一个人员多个组织节点；
- 手机号短信二次确认；
- 学号/工号登录；
- 彻底删除 `school_id`（当前固定为 1，后续单独重构）。
